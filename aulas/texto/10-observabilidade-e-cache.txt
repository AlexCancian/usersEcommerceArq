GET /health/pagamentos
{ "servico": "payment-service", "status": "degradado",

   "dependencias": { "banco": "ok", "kafka": "ok", "circuitoBancoCartao": "ABERTO" } }

Status      Quer dizer                                      Código HTTP
ok          tudo funcionando                                200
degradado   funciona, mas pior: sem cache, circuito aberto  200
fora do ar  não consegue trabalhar: sem banco ou sem Kafka  503

Um bom health testa de verdade: um SELECT 1 no banco, uma pergunta ao Kafka, um PING no Redis. "O processo
respondeu" não diz nada sobre as dependências.
Rápido e barato: ele é chamado a cada 10 s; nada de consulta pesada nem chamada a outros serviços.
                          VIVO × PRONTO

Pergunta                  Se a resposta for não                     Exemplo
                          reiniciar o container                     o processo travou num laço infinito
Está vivo? (liveness)
não olha dependências     parar de mandar requisições até melhorar  ainda subindo, ou sem o próprio banco

Está pronto? (readiness)
olha as dependências

Sem o próprio banco: vivo, mas não pronto. O readiness responde 503. O liveness continua 200: reiniciar o serviço não traria
o banco de volta.
Sem o banco do cartão: pronto, só degradado. O pagamento faz o que deve, recusar rápido: 200. Um 503 o tiraria do ar à
toa.
Dependência que só acelera (o cache) nunca tira o serviço do ar: no máximo, degradado.
No docker-class, dois endpoints: /health/live (só o processo) e /health/ready (as dependências; o /health é o mesmo). No
projeto, um /health com os três estados basta.

      CACHE

O trabalho mais rápido é o que não precisa ser feito.
Cache é guardar o resultado de um trabalho caro, num lugar rápido,
para não fazer de novo na próxima vez.
A vitrine é lida mil vezes para cada vez que um produto muda.

NO PROJETO: obrigatório, na vitrine do catálogo.
                           CACHE EXISTE EM TODA PARTE

        Navegador                      CDN                       Gateway               Aplicação                 Banco

Cache-Control: max-age=60  imagens e páginas, perto do  plugin proxy-cache do Kong  Redis: resultado de  o próprio banco guarda
                                         cliente                                          consultas       páginas em memória

Quanto mais perto do cliente, mais rápido, e mais difícil de apagar quando o dado muda: não dá para limpar o cache do
navegador de cada cliente.
Hoje: cache na aplicação, com Redis. É o que dá mais controle: o próprio serviço decide o que guardar e quando apagar.
Redis: um banco chave-valor em memória. Respostas em microssegundos, chaves com validade (TTL) e comandos simples:
GET, SET, DEL, INCR, EXPIRE.
                                     O PADRÃO CACHE-ASIDE

async function lerOuBuscar(chave, buscar) {                                1. Procura no cache. Achou: HIT, devolve.
                                                                           2. Não achou: MISS. Busca no banco e
   try {                                                                   guarda por 30 s (EX = TTL).
                                                                           3. Redis fora: OFF. Vai direto ao banco: o
      const guardado = await redis.get(chave);                             cache acelera, não sustenta.

      if (guardado) return { valor: JSON.parse(guardado), cache: 'HIT' };  O cabeçalho X-Cache na resposta deixa ver
                                                                           qual dos três aconteceu. Na docker-class:
   } catch {                                                               MISS 0,51 s, HIT 0,008 s.

      return { valor: await buscar(), cache: 'OFF' }; // Redis fora

   }

   const valor = await buscar();                // MISS: vai ao banco

   await redis.set(chave, JSON.stringify(valor), 'EX', 30);

   return { valor, cache: 'MISS' };

}
                             O DIFÍCIL: QUANDO APAGAR

"Só há duas coisas difíceis em computação: invalidar cache e dar nome às coisas." (Phil Karlton)

Estratégia      Como                                                    Onde vimos
Só o TTL        a chave expira sozinha; o dado pode ficar velho até lá  rede de segurança de todas
Apagar a chave                                                          docker-class: estoque:lista
Versão          toda escrita faz DEL; a próxima leitura busca o novo    referência: catalogo:versao
                toda escrita faz INCR numa versão; as chaves antigas
                param de ser lidas e expiram

Apagar é simples quando há uma chave só. Com muitas (cada filtro da vitrine é uma chave), a versão apaga todas de uma
vez com um único comando.
Esqueceu de invalidar? O cliente vê o preço antigo até o TTL vencer. Por isso o TTL é curto para dados que mudam e longo
para dados que quase não mudam.

O número da versão não fica dentro das peças. Ele fica guardado num lugar só (catalogo:versao) e aparece no NOME das chaves,

Como numa banca de jornal: estas são as cópias da "edição 7".

                                                        RESPOSTAS 1 E 2

1. O /health do pedidos deveria chamar o do catálogo? Não.
O health diz se o próprio serviço consegue trabalhar. Se o pedidos ficasse "fora do ar" porque o catálogo caiu, um orquestrador
reiniciaria o pedidos à toa, e uma queda viraria várias (falha em cascata). Além disso, os health checks chamando uns aos
outros multiplicam as chamadas. A dependência do catálogo aparece no 503 do checkout e no health do próprio catálogo.

2. Um pedido chegou com o banco do estoque fora. Ele se perdeu.
O stock-service recebeu o pedido.criado, deu erro ao gravar a reserva, e o kafka.js só registrou no log; o offset avançou e o
evento não volta. O pedido fica em AGUARDANDO_ESTOQUE para sempre. O certo: não confirmar o offset quando o erro é
passageiro (o evento volta), ou mandar para um tópico de erros (DLQ) e reprocessar depois. É a limitação listada no README
da referência.
                                                        RESPOSTAS 3 E 4

3. Quanto tempo o preço antigo aparece? Nenhum, se a invalidação funcionar; no máximo o TTL, se ela falhar.
A edição do admin faz a invalidação (DEL ou INCR da versão), e a próxima leitura já busca o preço novo. Se a invalidação falhar
(o Redis estava fora naquele instante), o TTL limita o estrago: 60 s na referência. E no checkout o preço é sempre consultado no
catálogo, não no cache da vitrine: ninguém paga o preço velho.

4. Cachear o GET /pedidos/:id? Não.
O cliente consulta várias vezes justamente para ver o status MUDAR (AGUARDANDO → PAGO). Com cache, ele veria o status
velho e consultaria mais ainda. É um dado de uma pessoa só, lido poucas vezes, e o banco do pedidos responde rápido. Cache
vale para o que muitos leem e muda pouco; para avisar mudança, o caminho é avisar (e-mail, WebSocket), não guardar.
