// A primeira regra que casar vale. metodo ausente = qualquer método.

const REGRAS = [

    { metodo: 'POST', caminho: /^\/auth\/login$/,  servico: 'usuarios', acesso: 'publico' },

    { metodo: 'POST', caminho: /^\/usuarios$/,     servico: 'usuarios', acesso: 'publico' },

    { metodo: 'GET', caminho: /^\/usuarios$/,      servico: 'usuarios', acesso: 'admin' },

    {             caminho: /^\/usuarios\/me(\/.*)?$/, servico: 'usuarios', acesso: 'logado' },

    { metodo: 'GET', caminho: /^\/(produtos|categorias)(\/.*)?$/, servico: 'catalogo', acesso: 'publico' },

    {             caminho: /^\/(produtos|categorias)(\/.*)?$/, servico: 'catalogo', acesso: 'admin' },

    {             caminho: /^\/(carrinho|pedidos)(\/.*)?$/, servico: 'pedidos', acesso: 'logado' },

];

✓ A ordem importa: GET /produtos casa com a regra pública antes de cair na regra de admin.
✓ Três níveis de acesso: publico (sem token), logado (qualquer token válido), admin (token com perfil admin).
✓ Rota que não está na tabela: 404 no próprio gateway.

  POR QUE NÃO USAR O NOSSO?

Escrever do zero ensina como funciona. Em produção, quase
ninguém mantém o próprio gateway. Faltaria:

  • Limite de requisições por cliente (rate limiting)
  • Balanceamento com verificação de saúde dos serviços
  • Cache de respostas, CORS, HTTPS, mTLS
  • Métricas, logs para vários destinos, painel de gestão
  • Anos de correções de segurança e desempenho

PRONTOS: Kong, Traefik, NGINX, Envoy, AWS API Gateway, Azure API Management.

Escala: o Kong não guarda estado da requisição. Para aguentar mais tráfego, sobem mais réplicas atrás de um balanceador,

A pergunta: os clientes se cadastram sozinhos. Como o acl sabe quem é admin, se não existe um consumer para cada pessoa?

Mudou o perfil no banco? Vale no próximo login: o token antigo continua com o perfil antigo até vencer (2 h). Por isso tokens têm vida curta.
Por que não um consumer por usuário? O serviço de usuários teria que chamar a Admin API do Kong a cada cadastro, o Kong precisaria
de banco, e um sumiço de sincronia deixaria alguém sem acesso.

                                        REDE INTERNA DO DOCKER: NINGUÉM DE FORA ALCANÇA

                                        usuarios  catalogo

Pessoa       JWT   KONG :8080

site ou app       valida e identifica

                  repassa com X-User-*

                                        pedidos   pagamentos

                                        seta laranja: chamada direta entre serviços, sem passar pelo Kong

Cliente → Kong: JWT emitido só por usuarios. O Kong valida, acha o consumer pelo perfil e confere o grupo.
Kong → serviço: o serviço confia nos X-User-* e não valida token. Ele só fala com quem está na rede interna.
Serviço → serviço (pedidos → catálogo; na docker-class, payment → order): direto, sem Kong, sem token. A proteção é não publicar porta.
E se não der para confiar na rede? Zero trust: cada serviço prova quem é com certificado (mTLS), em geral com um service mesh (Istio,
Linkerd). Fica de fora do nosso projeto.

       O QUE ENTREGAR

  1. Kong sem banco, com kong/kong.yml versionado. A 8080 é a única porta da API.
  2. Consumers cliente e admin com grupos; jwt achando o consumer pelo perfil do token.
  3. Rotas fechadas: logado com jwt (401); admin com jwt + acl (403). Acabou o catálogo aberto.
  4. correlation-id global e rate-limiting no login (10 por minuto por IP).
  5. usuarios é o único que emite JWT, com o perfil do banco. Os outros serviços leem X-User-*.
  6. Serviço pedidos: 3 tabelas, carrinho e checkout chamando o catálogo direto, com timeout.
  7. Nenhuma porta publicada além do gateway. Arquivos .http pelo gateway, mais o pedidos.http.
