   ANTES DE CODAR: QUAL BANCO?

Para cada serviço, escolham o banco e defendam a
escolha:

usuarios: e-mail que não pode repetir, senha, perfil, vários endereços por pessoa.
catalogo: um celular tem memória e cor; uma camiseta tem tamanho e tecido; um livro tem
autor e páginas.

REGRA: cada serviço escolhe o seu. Nada obriga os dois a usarem o mesmo banco.

                           USUARIOS: AS TABELAS (POSTGRES)

CREATE TABLE usuarios (

id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),

nome     TEXT NOT NULL,

email    TEXT NOT NULL UNIQUE,            -- não repete

senha_hash TEXT NOT NULL,       -- bcrypt, nunca a senha

perfil   TEXT NOT NULL DEFAULT 'cliente' CHECK (perfil IN ('cliente','admin')),

criado_em TIMESTAMPTZ NOT NULL DEFAULT now()

);

CREATE TABLE enderecos (

id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),

usuario_id UUID NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,

apelido  TEXT, cep TEXT NOT NULL, logradouro TEXT NOT NULL, numero TEXT,

complemento TEXT, cidade TEXT NOT NULL, uf CHAR(2) NOT NULL,

principal BOOLEAN NOT NULL DEFAULT false

);

SEED OBRIGATÓRIO: admin@loja.com / admin123 (perfil admin) e cliente@loja.com / cliente123 (perfil cliente,
com um endereço). Idempotente: rodar duas vezes não duplica.

                                         REVISÃO: ROTAS REST

Uma rota = verbo HTTP (a ação) + URL (o recurso).

GET /produtos         // lista
GET /produtos/:id     // busca um
POST /produtos        // cria
PUT /produtos/:id     // substitui inteiro
PATCH /produtos/:id   // altera uma parte (ex.: só o estoque)
DELETE /produtos/:id  // remove

✓ Substantivo no plural: /produtos, /usuarios. Nada de /criarProduto ou /getUser.
✓ Filtro vai na query string: GET /produtos?categoria=livros&busca=java
✓ Sub-recurso no caminho: GET /usuarios/me/enderecos
                    REVISÃO: STATUS CODES

Código              Significa                     No nosso projeto
200 OK              Deu certo e tem conteúdo      GET /produtos
201 Created         Recurso criado                POST /usuarios
204 No Content      Deu certo, sem conteúdo       DELETE /usuarios/me/enderecos/:id
400 Bad Request     Dados inválidos               Cadastro sem e-mail, preço negativo
401 Unauthorized    Não sabemos quem você é       Login errado, token ausente ou vencido
403 Forbidden       Sabemos quem é, mas não pode  Cliente tentando criar produto
404 Not Found       Não existe                    GET /produtos/id-que-nao-existe
409 Conflict        Conflita com o que já existe  E-mail já cadastrado, slug repetido
500 Internal Error  Erro nosso                    Nunca de propósito

Regra de bolso: 2xx deu certo · 4xx o cliente errou · 5xx o servidor errou.

                                    USUARIOS: AS ROTAS

Método  Rota                        Acesso   Retornos
POST    /auth/login                 público  200 { token, usuario } · 401 e-mail ou senha errados
POST    /usuarios                   público  201 usuário criado (sem senha) · 400 dados inválidos · 409 e-mail já existe
GET     /usuarios/me
PUT     /usuarios/me                logado   200 meus dados · 401 sem token
GET     /usuarios/me/enderecos      logado   200 dados atualizados · 400 dados inválidos
POST    /usuarios/me/enderecos      logado   200 lista dos meus endereços
DELETE  /usuarios/me/enderecos/:id  logado   201 endereço criado · 400 dados inválidos
GET     /usuarios                   logado   204 removido · 404 não existe ou não é meu
GET     /health                     admin    200 lista de usuários · 403 não é admin

                                    público  200 serviço e banco ok

O login devolve um JWT com id, e-mail e perfil, assinado com JWT_SECRET (variável de ambiente). Por enquanto, o próprio
serviço valida o token nas rotas /me; na próxima aula, o gateway assume.
                                     CATALOGO: AS ROTAS

Método  Rota                         Acesso   Retornos
GET     /produtos?categoria=&busca=  público  200 lista de produtos ativos
GET     /produtos/:id                público  200 produto · 404 não existe
POST    /produtos
PUT     /produtos/:id                admin    201 criado · 400 dados inválidos · 409 SKU já existe
PATCH   /produtos/:id/estoque        admin    200 atualizado · 400 dados inválidos · 404 não existe
DELETE  /produtos/:id                admin    200 estoque ajustado · 400 estoque negativo
GET     /categorias                  admin    204 desativado (ativo = false, não apaga) · 404
POST    /categorias                  público  200 lista de categorias
GET     /health                      admin    201 criada · 409 slug já existe

                                     público  200 serviço e banco ok

Rotas de admin, por enquanto, ficam abertas. O catálogo não deveria saber validar o token de outro serviço; isso é trabalho do
gateway, na próxima aula.
                               UM FORMATO DE ERRO PARA TODOS

Os dois serviços devolvem erros no mesmo formato. Quem consome a API sabe sempre onde
olhar.

// 409 Conflict em POST /usuarios
{ "erro": "Este e-mail já está cadastrado." }

// 400 Bad Request em POST /produtos
{

    "erro": "Dados inválidos.",
    "detalhes": ["preco deve ser maior que zero", "sku é obrigatório"]
}

✓ Nunca devolver stack trace nem mensagem do banco para o cliente.
✓ Nunca devolver senha_hash, nem dentro da lista de usuários do admin.
✓ Validação no serviço, não só no Postman: o banco é a última linha de defesa (UNIQUE, NOT NULL).

@usuarios = http://localhost:3001

### Login do cliente
# @name login
POST {{usuarios}}/auth/login
Content-Type: application/json

{ "email": "cliente@loja.com", "senha": "cliente123" }

### Meus dados: reaproveita o token da resposta do login
GET {{usuarios}}/usuarios/me
Authorization: Bearer {{login.response.body.$.token}}
